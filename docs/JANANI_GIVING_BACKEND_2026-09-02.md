# Janani Giving backend foundation

Date: 2026-09-02

## Purpose

Janani Giving is a commercial-social-impact layer for directing an approved share of Janani's distributable surplus to verified child-welfare organisations. It is deliberately separated from pregnancy, health, family, Care+, authentication, and subscriber data.

A Janani or Care+ purchase is a purchase of Janani services. It is **not** a charitable donation by the user. Janani separately calculates and approves its own Giving allocation after revenue, refunds, taxes, operating costs, and reserve requirements are accounted for.

## Financial flow

The intended accounting model is:

1. Gross Janani commercial revenue.
2. Less app-store/platform fees.
3. Less refunds and chargebacks.
4. Less applicable taxes.
5. Less operating costs required to run Janani safely and reliably.
6. Less the approved sustainability reserve allocation.
7. Result: distributable surplus.
8. Apply the approved Giving rate for that accounting period.
9. Transfer only to a verified child-welfare organisation.
10. Reconcile the bank transfer and supporting evidence.
11. Publish only the sanitized donation record.

The migration stores accounting-period figures privately. The public website does not receive Janani's private accounting records.

## NGO verification gate

An organisation cannot be published as a verified Janani Giving recipient unless all of the following are true in the backend:

- due-diligence status is `verified`;
- organisation bank ownership has been verified;
- child-safeguarding review has been verified; and
- `verified_at` has been recorded.

Additional legal/tax checks appropriate to the jurisdiction should be completed outside the software before the organisation is marked verified. The software does not substitute for accountant or legal review.

## Donation lifecycle

Private statuses:

`draft -> approved -> transferred -> reconciled -> published`

`void` is available for a donation that should no longer progress.

Only a `reconciled` donation can be passed to `janani_giving.publish_donation(uuid)`.

Publication additionally requires:

- a transfer timestamp;
- a reconciliation timestamp; and
- a currently verified organisation satisfying the verification gate.

The public reference is generated by Janani (`JG-YYYYMM-XXXXXXXX`). The private bank/payment reference is never copied to the website ledger.

## Public website boundary

The only relation intended for anonymous website reads is:

`public.public_giving_ledger`

Allowed public fields:

- `organisation_name`
- `cause`
- `amount_inr`
- `transferred_at`
- `verification_status`
- `public_reference`

The ledger deliberately excludes:

- NGO registration/tax identifiers;
- bank details or internal transfer references;
- private receipt-storage paths;
- internal notes;
- Janani revenue and cost accounting;
- subscriber or billing identities;
- user IDs;
- emails;
- family data;
- pregnancy data;
- health or medication data;
- journal content;
- Care+ conversations; and
- authentication or device information.

Anonymous and authenticated clients receive SELECT-only access to the public ledger. Publication and unpublication functions are service-role-only.

## Audit model

Giving audit events are append-only. Organisation and donation changes are recorded automatically, and publication/unpublication creates an explicit publication audit event.

The website must never estimate or fabricate donation totals. If the public ledger is unavailable, the website should display an unavailable/empty state rather than cached or inferred financial values.

## CI safety gate

PR #68 includes `.github/scripts/validate-giving-migration.mjs`, run by the normal Janani Quality workflow whenever the Giving migration exists. It fails closed if the private Giving schema is exposed to `anon` or `authenticated`, if public website roles receive write access, if reconciliation/NGO-verification publication gates are weakened, if publish/unpublish functions become client-callable, or if private accounting/NGO/user/pregnancy/health identifiers are added to the public ledger.

Janani Quality run #527 passed this Giving-specific guard together with dependency audit, TypeScript, lint, Expo Doctor, legal-site validation, and Expo public-config validation on commit `f02d9e9edf0a9ae5de9da68b2c6a7e688436b3ac`.

## Production application gate

**Do not apply `20260902043000_janani_giving_foundation.sql` to the live Janani project yet.**

The Janani repository still has an open migration-history reconciliation task for production. Before applying this new migration:

1. Restore reliable Supabase management access.
2. Re-read the exact production migration history and deployed SQL.
3. Complete or explicitly resolve the existing migration reconciliation.
4. Replay the reconciled migration chain against a clean staging database.
5. Apply the Giving migration to staging.
6. Run Supabase security advisors after the DDL change.
7. Verify anonymous clients cannot read `janani_giving.*`.
8. Verify anonymous clients can read only the six approved public ledger fields.
9. Verify authenticated app users gain no new private Giving access.
10. Verify service-role publication refuses draft, approved, transferred, unreconciled, or unverified-organisation donations.
11. Only after those checks pass, apply the migration to production.

## Website activation gate

Keep `givingLiveEnabled = false` in `Janani-website/assets/runtime-config.js` until all of the following are complete:

- production migration applied and security-reviewed;
- the website has the correct Janani Supabase URL and active publishable key;
- one test donation has completed the private lifecycle in a non-production environment;
- public ledger output has been checked for sensitive information; and
- the website ledger has been tested for empty, unavailable, and populated states.

The first real production donation should still require human approval and bank reconciliation. Fully autonomous fund transfers are out of scope for this foundation milestone.
